## 0. 一句话结论（Q39 修正版）

**地图只做一件事：把当天的点位和动线画在页面里。做法只有一种 —— 内嵌一张静态图。**

| 做法 | 要 Key 吗 | 用不用 | 依据 |
|---|---|---|---|
| **L3 · 内嵌路线图** | ✅ **要自备 WebService Key**（**不需要配置任何连接器**） | ✅ **唯一做法** —— **每日行程里每天一块**，画当天点位 + **真实道路走向** | Q31 立，Q35/Q36/Q37/Q38 实测跑通 |
| ~~免 Key 外链~~（旧 L1） | ❌ 不要 | ⛔ **移除** | **Q39 用户实测**：点开提示「**缺少 Key 和账户**」、看不到路线图，**体验差** |
| ~~iframe 嵌入~~（旧 L2） | ❌ 不要 | ⛔ **移除** | **离线打开是空白** —— 破坏"双击即开"的承诺 |
| ~~行程全貌放地图~~ | —— | ⛔ **移除** | **Q39 用户裁定**：全貌只有「脑图 + 游玩要点口诀」，**把地图放全貌是理解任务错误** |

**没有 Key 时怎么办**：**不出现地图位** —— 当天的动线用**文字 + 序号**表达（`象鼻山 → 芦笛岩 → 七星公园`），
**不留空白框、不写"此处应有地图"、也不提示"可惜没有地图"**。

> ★ **"页面里要有地图"只有 WebService 静态图这一条路** —— 与**「把攻略存进腾讯地图 App」**
> （那是**指南制作 MCP** 干的、另一件互不相干的事）**毫无关系**。
> **"地图嵌进 HTML"不需要在连接器面板里配置任何东西**，只要把 Key 交给脚本。判定表 → `mcp-integration.md` §1.1。

### 为什么免 Key 的路子走不通（必须提前知道）

腾讯地图有一组公共页面（`mapapi.qq.com/web/claw/*`），内置了一把默认 Key（浏览器端 Key），**任何人拼 URL 就能打开**——
但它的权限**只够渲染底图**：

| 功能 | 走什么通道 | 内置 Key | 结果 |
|---|---|---|---|
| 地图渲染 / 图钉摆放 | JS SDK 渲染 | ✅ 有「地图展示」权限 | 正常 |
| 图钉详情 / 周边搜索 | WebService API | ❌ 无权限 | **报错** |
| **路线规划** | WebService API | ❌ 无权限 | **报错 ← 最痛** |

→ 所以"免 Key 能看地图"这件事，**能给到的只有"一个孤零零的底图 + 图钉"**，
既没有路线、还要跳出去。**读者点进去看到的是报错弹窗** —— 这就是它被移除的原因。

## 1. 免 Key 公共页面：留档（**不作为产物**）

> **这一节的用途只有一个：说明"为什么不用它"，避免以后有人再试一遍。**
> ⛔ **这三个端点一律不进产物**（无外链、无 iframe）。

### 1.1 周边搜索页

```
https://mapapi.qq.com/web/claw/nearby-search.html?center={纬度},{经度}&keyword={关键词}&radius={半径米}
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `center` | 建议填 | 格式 **`纬度,经度`**（⚠️ 纬度在前）。**不填会默认落在深圳南山**（`22.540503,113.934528`） |
| `keyword` | 建议填 | 搜索类别，如 `餐厅` / `奶茶` / `超市`。不填默认「奶茶」 |
| `radius` | 可选 | 搜索半径（米），默认 `5000` |

> ⚠️ **静默失败风险**：不传 `center` 不会报错，而是**安静地展示深圳的搜索结果**。
> ⚠️ **边界**：页面能打开、能显示周边点位；但**点开某个点的详情**会触发 WebService → 报「此key未开启WebserviceAPI功能」。

### 1.2 旅行规划页

```
https://mapapi.qq.com/web/claw/travel.html?spots={URL编码的JSON}&recommend={restaurant|hotel|both}
```

`spots` = URL 编码后的 JSON 数组，元素 `{name, lat, lng, desc}`。

#### ⚠️ 三个必须记住的硬约束（源码级实测）

**① 景点数量必须 ≥ 2。**
源码 `if (Array.isArray(parsed) && parsed.length >= 2)`。
**只传 1 个景点，整包会被丢弃，页面回退为北京默认景点**（故宫 / 颐和园 / 香山 / 环球影城）—— **静默失败。**

**② `recommend` 传多值无效。**
白名单 `['restaurant','hotel','both']` + `.includes(recParam)`。
传 `restaurant,hotel` **被静默忽略**，最终按默认 `both` 处理。
（注：`tmap-lbs-plugin` 官方文档写的 `recommend=restaurant,hotel` **是错的**，不要照抄。）

**③ `desc` 字段可用但文档未记载。**（白捡的展示位，未用）

> ⚠️ 这个页面的**"路线规划"按钮会报错**（路线规划必须走 WebService）——
> 用户 Q39 反馈的「点开提示缺少 Key 和账户」就是它。**不要把"这一天怎么走"的期望挂在这类页面上。**

### 1.3 轨迹地图页

```
https://mapapi.qq.com/web/claw/trail-map.html?data={URL编码后的在线JSON地址}
```

`data` 必须**是外部能访问到的在线地址**（页面会 `fetch` 它）。在"单个 HTML 文件"的交付形态下**本地路径不可用** → 默认不使用。

## 2. ⚠️ 权限边界：用户会看到什么

用户实跑回报的两个报错，**是同一个根因**：

| 现象 | 触发路径 |
|---|---|
| 「**此key未开启WebserviceAPI功能**」 | 点开图钉看详情 / 看周边 |
| 「**路线规划失败，请检查网络或 API Key 配置**」 | 点每日动线的路线规划 |

**根因**：页面用内置 `DEFAULT_KEY` 加载 GL JS SDK（`libraries=service`），**并在页内真调 WebService API**。
而该内置 Key **只开通「地图展示」权限，未开通「WebServiceAPI」权限**。

> 🔧 **别被那句话带偏**：第二句提示是页面 `.catch` 里**硬编码的 UI 文案**，
> 它把"权限不足"包装成了"网络或配置问题"。**这不是环境问题，是权限边界。**

### 想拿到地图？（Q31 立，Q35 按实测校准）

**需要用户自备一把腾讯位置服务 Key。** 申请四步：

| 步 | 去哪 | 做什么 |
|---|---|---|
| 1 | [lbs.qq.com/dev/console/key/add](https://lbs.qq.com/dev/console/key/add) | 登录 → 创建应用（名称随意，如"我的旅行攻略"） |
| 2 | 同上 | 在该应用下**添加 Key** → 类型勾选 **「WebServiceAPI」** |
| 3 | ★ [配额页](https://lbs.qq.com/dev/console/quota/account) | 看「**已分配/总额度**」两列，点 **「一键分配」** 把额度分给要用的接口 —— **这一步最容易漏，漏了就一调用就 121** |
| 4 | 交给 agent | 粘贴 Key / 设环境变量 `TMAP_WEBSERVICE_KEY` / 存进 `./.workbuddy/tmap_key.txt` |

#### 🔧 给 Agent 的承接规范（让小白“给 Key”零试错）

这不是给用户的固定脚本，而是**Agent 自己的提示时机 + 承接动作**，照着这几条做，别临场发挥：

- **提示时机**：在交付前、且当行程有“每天 2+ 个点位”时，主动问一句“有一个增强项，要不要配腾讯地图 Key？没有也能出完整攻略，只是不内嵌实时路线图”。**不要开局就问**，也别在交付后追加。
- **提示内容**（一句话给全，不罗列）：给用户 **两个网址** —— `lbs.qq.com/dev/console/key/add`（建应用+建 Key，**记得类型勾选「WebServiceAPI」**）与 `lbs.qq.com/dev/console/quota/account`（**点「一键分配」让额度生效，否则一调就报 121**）；让用户把整串 Key 贴回对话框。
- **承接动作（拿到 Key 之后）**：**先跑 `python scripts/make_route_map.py --probe`** 一次看清五个接口谁还活着。**不许跳过这步直接出图。**
- **报错一步定位，不试错**（对应上表）：

| probe 报错 | Agent 的下一步（只准这一句，别让用户睡调） |
|---|---|
| `199 此key未开启WebserviceAPI功能` | 让用户回应用设置，**把 Key 类型勾上「WebServiceAPI」** |
| `311 key格式错误` | 让用户**重新完整复制 Key**，别漏字符 |
| `121 每日调用量已达上限` | 让用户去[配额页](https://lbs.qq.com/dev/console/quota/account) **点「一键分配」**；当天实在不行就说明次日自动重置 |
| 全部正常 | 收下 Key，**存 `./.workbuddy/tmap_key.txt` 或环境变量 `TMAP_WEBSERVICE_KEY`**，进§3 出每日路线图 |

- **承前不承后**：用户全程**没给 Key 就自动降级**（§4.3 降级规则：动线用文字+序号表达），**流程照跑**，Agent 不卡、不反复追问。

#### ⚠️ 拿到 Key 之后，最可能卡住的地方（Q35 实测）

| 你看到的 | 含义 | 怎么办 |
|---|---|---|
| `status:121 此key每日调用量已达到上限` | **该接口**当日额度用尽 | ① **次日自动重置**；② 去[配额页](https://lbs.qq.com/dev/console/quota/account) 点「**一键分配**」 |
| `status:199 此key未开启WebserviceAPI功能` | Key 没勾 WebServiceAPI 能力 | 回应用设置勾上 |
| `status:311 key格式错误` | Key 没填对 | 核对整串 Key |

> ★ **实测（Q35）**：一把刚申请的 WebServiceAPI Key ——
> **`staticmap` 第 1 次成功、第 2 次起就报 121**；`direction` / `distance` / `place` 各成功一两次后同样 121。
> → **不是 Key 有问题，是额度没分配 / 极低。去配额页点「一键分配」。**
> → 排查命令：`python scripts/make_route_map.py --probe`（各接口各打 1 次，一次看清谁还活着）。

#### 各接口地址（Q35 实测可用清单）

| 服务 | 地址（前缀 `https://apis.map.qq.com/ws/`） | 实测 | 本项目用途 |

## 3. 坐标系规范（⚠️ 本项目统一口径）

| 平台 | 顺序 | 示例 |
|---|---|---|
| **腾讯地图（本项目采用）** | **`纬度,经度`**（lat, lng） | `29.5627,106.5785` |
| ~~高德地图（已退场）~~ | ~~`经度,纬度`~~（lng, lat） | ~~`106.5785,29.5627`~~ |

### 强制规则

1. **全项目统一使用腾讯口径 `纬度,经度`。**
2. **字段名必须显式写成 `lat` / `lng`**，禁止使用位置型数组（如 `[29.5627, 106.5785]`）——
   用字段名消除顺序歧义，这是唯一可靠的防错手段。
3. 高德 URI 方案**仅作为"腾讯端点整体不可用"时的备选**，且**切换时必须做坐标顺序转换**，不可直接搬。

> 🔧 **为什么退场高德**：两套坐标系顺序相反，同时维护两套映射是纯粹的出错来源。
> **交付落点始终是那个 HTML 文件**（不是任何地图账号）。

## 4. 在网页里怎么用（**Q39 已落地到模板**）

**形态只有一种**：`assets/template.html` 里每天行程块内的 `.routewrap`，内含**一张 base64 内联的静态图**。

| 项 | 规定 |
|---|---|
| **位置** | **每日行程 · 当天块内**（时间线之后、页脚之前）—— **每天一块** |
| **不在哪** | ⛔ **行程全貌里不放**（Q39 用户裁定）；⛔ 不放在"行程总览" |
| **形态** | `<div class="routewrap"><img src="data:image/jpeg;base64,…"><div class="rfoot">地图：腾讯位置服务静态图 · 路线为非导航级示意</div></div>` |
| **需要联网吗** | ❌ 不需要 —— 它就是页面里的一张图 |
| **某天不放地图** | **整块删除 `routewrap`**；**不留空占位、不写"此处应有地图"** |

### 4.1 坐标从哪来（⚠️ 硬规则）

**不得猜测坐标。** 来源只认三种：

| 来源 | 说明 |
|---|---|
| 官方 / 权威公开资料 | 景区官网、政府公开信息、权威地图站点；**能说出依据** |
| 用户投喂 | 用户自己给的坐标、地图链接、截图 |
| 用户自备腾讯地图 Key | 走 WebService（`place/v1/search` / `geocoder/v1`） |

**三种都取不到 → 那天不放地图**，只留文字动线。
**核心约束：宁可不出地图，不可出错的坐标。**

### 4.2 L3 出图全链路（**需自备 WebService Key**）

**★ 用脚本，不要手搓**：

```bash
python scripts/make_route_map.py --probe                                  # 先诊断 Key（各接口各打 1 次）
python scripts/make_route_map.py --demo                                   # 离线自检解码与抽稀，不联网
python scripts/make_route_map.py --input trip.json --out route.json --split-days
```

`--split-days` = **按天各出一张图**（对应 §4 的"每天一块"）。
输出 `route.json` 里每天一项：`{day, img_b64, max_dev_m, dist_m, dur_min, url_len}`。
失败时返回 `ok:false` + 可执行建议，**调用方据此整块删掉那天的 `routewrap`**。
输入格式参见 `scripts/example_trip.json`。

**Key 的三种给法**（按优先级）：`--key` → 环境变量 `TMAP_WEBSERVICE_KEY` → `--key-file`（默认找 `./.workbuddy/tmap_key.txt`）。

> ⚠️ **Key 是私密凭据**：存工作区 `.workbuddy/` 即可，**绝不写进 SKILL.md、不提交仓库、不贴公开对话**。
> **产物里只有图，没有 Key** —— 转发是安全的。

#### 生成链路

```
① 收齐当天坐标（来源见 §4.1 硬规则）
→ ② direction/v1/driving 逐段算路，拿 polyline
→ ③ 解 polyline → **RDP 抽稀**（★ 按 URL 预算自动定点数）
→ ④ staticmap/v2 出 PNG（markers 标景点 + path 画「白底彩线」）
→ ⑤ PNG 转 JPEG → base64 内联进当天块
→ ⑥ 同一天重复 ①–⑤（每天一张，各自独立）
```

> ★★ **三个「看不见但致命」的坑**（Q37 / Q38 实测，本模块此前写错不止一次）：
>
> **① 各天必须各占一个独立 `path` 参数 —— 既不能首尾相连，也不能用 `;` 串在一起**：
> 首尾相连 → 两天之间**凭空画一条直线**（桂林实测 **718 m** 与 **3,024 m**，横穿市区、极其刺眼）；
> 用 `;` 串在一个 `path` 里 → 服务端把整条 path 渲染成**闭合填充多边形**（灰块占 **32.7%** 画面、
> 被裁切 = 用户肉眼抓到的「**灰色半透明三角形，向下顶到/超出地图边界**」）。
> ✅ **正解 = 重复 `path` 参数**（`&path=…&path=…`）；**点与点之间仍用 `|`**（改成 `;` → **一个像素都不画**）。
>
> **② `weight` 几乎不改变渲染结果。** 实测 `weight` 5 / 10 / 20 三档两两差分只有 **0.7–0.9%**（抗锯齿抖动）；
> 服务端**会校验 1–20 范围**（超限报错），但**并不按它渲染**，线宽基本固定（约 **45 px 白底 / 20 px 红线**）。
> **想调粗细是调不动的，别再试。**
>
> **③ `markers` 的 `color` 参数完全无效。** 传任意值一律渲染成**青蓝 (100,188,214)**、传什么都一样；
> **不传**才是默认**红 (199,66,66)**。`color:#RRGGBB` 或省略 `0x` 前缀 → 直接请求失败。
> → 因此**餐厅不进内嵌地图**（图钉长得一模一样，加上去只让读者混淆，见 §4.4）。

#### ★ polyline 的真实格式（**实测所得，网上写法不适用**）

`direction` 返回的 `polyline` **不是** Google 那种压缩字符串，而是一个**扁平数字数组**：

```
[25.263805, 110.2948, 13, 395, 0, 0, 534, -7, ...]
 └── 首点纬度 ──┘└─ 首点经度 ─┘└Δlat┘└Δlng┘ └─ 第3点 ─┘
```

- `[0]`、`[1]` = 首点**绝对**经纬度（度）
- 其后**每 2 个** = 下一点的 `Δ纬度, Δ经度`（单位 **1e-6 度**，逐个累加）
- **点数 = `len(polyline) / 2`**
- ⚠️ `steps[].polyline_idx`（如 `[392, 401]`）指的是**原始数组下标**，**不是解出的点序号** —— 当点索引用会越界

> ★ **实测校验（Q35）**：桂林 象鼻山→芦笛岩，`len=402` → 解出 **201** 点；首点与请求 `from` 完全吻合；
> **累计距离 9121 m vs 官方 9104 m，误差 0.2%**。自检：`python scripts/make_route_map.py --demo`

#### ★ 抽稀与 URL 预算：点数是被 URL 上限卡死的

**先纠两个错**（都出在本模块上一版，Q37 实测推翻）：

| 上一版写的 | 真相（Q37 实测） |
|---|---|
| 「200 点 = 4,223 字符 ❌ 超 URL 上限」 | 那是**未实测的字符数估算** |
| 「URL 10,296 字符仍出真图 → URL 不是约束」 | **那是 `--selftest` 的 dry-run 输出，从未真的发过这个请求。** 真出图的样本其实只有 60 点、URL 约 3.5 K |

**URL 长度是硬约束，上限约 8192，超了网关直接返回 `414 Request-URI Too Large`（HTML，不是 JSON）：**

| 请求 | URL 长度 | 结果 |
|---|---|---|
| 200 点 × 1 层（6 位小数、全编码） | 5,167 | ✅ |
| 400 点 × 1 层（同上） | 10,167 | ❌ 414 |
| 300 点（5 位、不编码 `,` `\|` `:`） | 5,859 | ✅ |
| 400 点（同上） | 7,759 | ✅ |
| 500 点（同上） | 9,659 | ❌ 414 |

→ 取 **7800 作安全值**。两个省字符的手段（均已实测被接受）：
**① 坐标降到 5 位小数**（≈1.1 m 精度，画线足够）；**② `,` `\|` `:` 不做百分号编码** —— 靠 `urllib` 直发，
不能让 `requests` 重新编码。合计省约 **30%**，直接换成更多点数。

**点数怎么定：由预算反推 + 用实测 URL 长度闭环，不要手写常数。**
一张图能画多少点 = `(7800 − 固定开销) ÷ (层数 × 每点字符数)`；脚本组装后**实测长度**，超了按比例降点重试（最多 3 轮）。
🔧 **Q38 修完预算公式**（分母少乘一个 `layers`、每点按 **19** 字符而非 14）后**一轮即收敛**：189 点 / URL **7,728**。
**但每天一张之后，URL 预算按"当天点串"单独算**（点更少 → 单天预算更宽松 → 可给每天更高的 RDP 精度）。

**抽稀用 RDP（按最大偏离），不用等弧长。**
等弧长在长直路上照样布点、急弯处反而点不够 —— "点数花光了，弯还是被切掉"。
RDP 按**最大偏离**分配点：直路几乎不占点、弯道自动加密。

| 抽稀方案 | 对真实道路**最大偏离** | 图上表现（1600 px 宽、8.64 m/px） |
|---|---|---|
| 等弧长 60 点（**修复前实际用的**） | **144 m** | ≈17 px，**明显斜切街区** |
| 等弧长 200 点 | 60 m | ≈7 px，轻微 |
| **RDP 189 点（Q38 修复后）** | **5.7 m** | ≈**0.65 px**，肉眼不可辨 |

> ★ **偏离度是硬指标，写进 `route.json` 的 `max_dev_m`** —— 超 60 m 脚本会告警。
> **判"贴不贴路"不要靠肉眼、也不要靠"点数够不够多"这种代理指标，直接看这个数。**

#### 静态图 API V2 参数（**逐条实测校对过**）

| 参数 | 值 | 实测说明 |
|---|---|---|
| `center` | `纬度,经度` | 当天点位的包围盒中心（**不是全城中心** —— 每天各自算） |
| `zoom` | 1–18（`scale=2` 时需 4–17） | **按 Web Mercator 反解**（Q37 重写）：用两个相距 1005.7 m 的标记点标定，zoom 13 / 14 / 15 实测与理论偏差均 **< 0.4%**。⚠️ **只接受整数**（`13.5` / `13.7` → `status=348`），每档差 **2 倍**视野 → "内容占画面偏小"是"内容尺度落在两档之间"的**必然**。⚠️ `w1`/`h1` 传参必须是 **scale=1 语义**的像素数（传 `w*scale` 会让覆盖高估 2 倍 → zoom 偏大 1 档，实测 **3/11 景点被切出画面**） |
| `size` | `宽*高` | ★★ **真正的约束是"输出像素总数"**：(宽×scale)×(高×scale) ≤ **约 160 万**，超出报 `348 参数错误`。官方文档称"`size` 上限 1680*1200"**不成立**（202 万像素实测被拒） |
| `scale` | `1` / `2` | 高清倍率。**推荐 `800*500` + `scale=2` → 输出 1600×1000，恰在 160 万内** |
| `markers` | `size:large\|lat,lng\|lat,lng` | ✅ 多点在同一参数内用 `\|` 串起可用；`size:large` 足够醒目。⚠️ **别传 `color`**（见上"坑 ③"） |
| `path` | `weight:10\|color:0x…\|lat,lng\|…` | ✅ 语法可用。**点与点之间用 `\|`**；**要画多条互不相连的线，就重复 `path` 参数**。⚠️ `weight` **只能 1–20**，但**几乎不改变渲染** |
| `path`（再来一条） | `weight:20\|color:0xFFFFFF\|…` | ★★ **白描边** —— 见下节，这是让动线可见的关键 |
| `maptype` | `roadmap`（默认）/ `satellite` / `hybrid` | **没有"简化底图"参数** —— 底图 POI 密度改不了 |
| `key` | 你的 WebService Key | —— |

**不支持**：`fillcolor`（报 `path格式错误`）。

#### ★★ 描线必须"白底 + 彩线"两层（**最关键的一条发现**）

**单条彩线会被底图吃掉。** 服务端对 `path` 做了**半透明叠加** —— 给纯色，出来也是淡的：

| 提交的颜色 | 渲染后的平均色 | 彩色度 (R−G) |
|---|---|---|
| `0xFF0000` 纯红 | (179,123,118) | **+56** ← 最跳 |
| `0xE8552B` 亮橙红 | (174,143,128) | +31 |
| `0xB5502A` 朱磦 | (162,142,128) | +20 |
| `0x000000` 纯黑 | (119,123,118) | −4（无彩） |

**做法**：同一条点串**发两个 `path` 参数** —— 底层粗白线、上层细彩线：

```
path=weight:20|color:0xFFFFFF|<点串>      ← 白描边（更粗）
path=weight:10|color:<主色>|<点串>        ← 主色动线
```

对比度是**数量级**的差异：白边把彩线从路网与 POI 里"抠"出来，一眼能追。**不加白边 = 白画。**
（脚本默认已开 `path_halo`；`path_weight = 5 × scale`，白底自动取 2 倍宽。）

> ★ **配色结论与直觉相反**：**颜色越饱和、出来越跳**。
> `0x2F7D5C`（青绿）实测**命中率几乎为 0** —— 底图是大片绿地与水系，同色系直接隐身，**绝不能用于描线**。
> ★ **主色已定 `0xFF0000` 纯红**（Q37 用户裁定，D23 关闭）。
> 已知副作用：**底图自带约 10 个红色 POI 团块**，与纯红动线有局部混淆 —— **用户已知并接受，不纠结**。
> 页面本身仍守纸本中国风；**但地图是功能性元素，服从"看得清"而不是"配色雅"。**

**诚实命名（文案不能省）**：

| 画法 | 需要 | 图上的线是什么 | 页面文案 |
|---|---|---|---|
| **点位与顺序示意** | 只要静态图 | 点位之间的**直线** | 「**点位与顺序示意**」 |
| **真实道路走向**（推荐） | 加 `direction/v1/driving` + 解码 | **沿真实道路的折线** | 「**真实道路走向，非导航级**」 |

> 把真实路径点喂给 `path`，画出来就是**道路走向**。
> 但它**仍不是导航级**（无转向指引、无实时避堵）—— 文案里的"**非导航级**"不能省。
> 模板 `.rfoot` 已内置「地图：腾讯位置服务静态图 · **路线为非导航级示意**」，**不要改成"路线规划"**。

#### 体积（**每天一张 → 必须重新算总账**）

| 项 | 规定 |
|---|---|
| 单张路线图 | 原始 PNG（1600×1000）约 **1.6 MB** → 本地转 JPEG（**q62–q78**），**目标 ≤100 KB / 张** |
| 每天一张的总量 | **5 天 ≈ 500 KB**（原始图）；**base64 后 ×1.33 ≈ 660 KB** |
| **整页图片总预算** | **≤3 MB（HTML 文件，图片已 base64）** |
| 实测参考 | 桂林 5 天 / 16 张图（封面 1 + 景点 10 + 分类 5）→ 交付页 **1.70 MB** |
| 超了怎么办 | **按序降级**：① 降 JPEG 质量 → ② 缩短路程中间的抽稀点数（不改 `max_dev_m` 判据）→ ③ `size` 降到 `720*450@scale=2` → ④ **最差**：只给天数最长的 2–3 天出图，其余用文字动线 |

> ⚠️ **上限是天花板，不是目标。** 目标是**整页压在 2.5 MB 以内**；
> 一旦逼近 3 MB，"双击即开"的体验就开始受损（尤其手机打开）。

### 4.3 「吃什么」写店名怎么取证（Q39 新增 · `place/v1/search`）

**"吃什么"是刚需，必须写真实店名**（作用与景点同等，见 `content-model.md` §5）。店名从哪来：

```bash
# 按城市搜（品牌 / 老店 / 地标类）
place/v1/search?boundary=region(桂林,0)&keyword=啤酒鱼&page_size=10&key=…

# 按坐标搜附近（★ 更常用：「这一带吃什么」）
place/v1/search?boundary=nearby({纬度},{经度},{半径米})&keyword=米粉&page_size=10&key=…
```

| 项 | 说明 |
|---|---|
| **两种 `boundary` 都可用** | `region(城市,0)` 与 `nearby(lat,lng,半径)` **均 `status=0`**（Q39 实测 11 次全部成功） |
| **返回什么** | 真实**店名** + 完整**地址** + `location.lat/lng`（可直接喂给景点卡坐标 / 距离计算）+ `category` |
| **不返回什么** | ⚠️ **招牌菜**、**人均** —— 这两个 API 不给。若来自模型判断，**语气上要区分开**（写"以啤酒鱼出名"，不要写成像核实过的参数） |
| **写进哪里** | **当天时间线的 `li.food`**：`{餐次 · 店名}` + 招牌 / 一句理由 / 人均 / **与上一站的距离** |
| **写进地图吗** | ⛔ **不进**（§4.2 坑 ③：`markers` 颜色无效 → 餐厅图钉与景点图钉长得一样，只会混淆）。要表达"顺不顺路"用**文字距离** |
| **核实纪律** | 店名与位置属**公共资源信息**：数据层带 `verify` + `source` + `checked_at`；**页面上只写一行** `✅ 已核验（基于腾讯地图）`（不写"POI 检索"、不写日期）。**找不到可靠店名就如实说明（不加核验行），绝不编一个听起来很像的店名** |

**Q39 实测取证样本**（桂林 / 阳朔，11 次调用全 `status=0`）：

| 检索 | 命中（节选） |
|---|---|
| `region(桂林,0)` + `椿记烧鹅` | 椿记烧鹅（杉湖店 / 万象城店 / 高新店 / 叠彩店 / 临桂店）**5 家**——同品牌多分店，写店名时必须带**分店名** |
| `region(桂林,0)` + `阿甘酒家` | 阿甘酒家 **5 家** |
| `region(桂林,0)` + `桂林米粉` | 老店 / 连锁共 **10 家** |
| `nearby(兴坪…,2000)` + `啤酒鱼` | 刘姐 / 梁姐 / 谢三姐金奖 / 古镇 / 金牌烧鹅 / 佳鸿 **6 家** |
| `nearby(西街…,1500)` + `啤酒鱼` | 大师傅 **5 家分店** / 刘姐 —— **同一品牌多分店，必须带分店名** |
| `nearby(遇龙河…,3000)` + `农家菜` | 印象农家饭 / 滕哥 / 渔乡 / 渔坊 / 钟师傅 / 龙泉湖农庄 **6 家** |
| 地标类 | 富里桥 ✅ / 月亮山 ✅（可作坐标补全） |

> ★★ **店名是"事实"，不是"建议"** —— 它和票价一样要能溯源。
> **同品牌多分店是常态**：写 `椿记烧鹅（杉湖店）`，不要只写 `椿记烧鹅`（读者会找到隔壁区那家）。

## 5. 降级规则

| 情况 | 处理 |
|---|---|
| 用户提供了 WebService Key、坐标齐全、当天 ≥ 2 个点 | ✅ 走 **L3**，当天一块图 |
| 用户没给 Key | **不走地图** → 当天用**文字 + 序号**表达动线。**不提示"可惜没有地图"、不留空占位** |
| 当天只有 1 个点 | **不出图**（没有可画的动线），只留文字 |
| 坐标缺失或不确定 | **不出图**，标注"位置待确认"—— **绝不猜坐标** |
| Key 报 `status:121` | **当天不出图、不重试**（同日重试必然还是 121，白耗配额）；提示去配额页「一键分配」或次日再试 |
| `status:199` / `311` | 同上（Key 未开 WebServiceAPI / Key 格式错） |
| `348 参数错误` | 脚本已内置兜底：**像素守卫**（自动降 scale / 缩 size）+ **失败后自动改 `scale=1` 重试一次** |
| 某天请求失败，其他天成功 | **只删那天那块** —— 其余天照常出图（**每天独立，互不牵连**） |
| 腾讯端点整体不可用 | 降级到高德 URI（**须转换坐标顺序**）—— ⚠️ 但**产物里不放外链**，所以实际做法是**全部改用文字动线** |

> **核心约束：宁可不出地图，不可出错的坐标。**

## 6. 明确不做（避免误用）

- ❌ **不做免 Key 外链地图**（旧 L1 —— Q39 移除：点开提示"缺少 Key 和账户"）
- ❌ **不做 `<iframe>` 嵌入**（旧 L2 —— 离线打开是空白）
- ❌ **不在「行程全貌」放地图**（Q39 用户裁定：全貌只有脑图 + 游玩要点口诀）
- ❌ **不引入腾讯地图 JS SDK、不做自定义地图组件**（单文件 HTML 的体积与稳定性考虑）
- ❌ **不把 WebService curl API 当必需路径**（静态图 / 路径规划 / POI 搜索都要 Key）。✅ **"可选加档"是允许的**：用户自备 Key 时走 **L3**。**"非必需"不等于"不许用"。**
- ❌ **不硬依赖任何 MCP / 连接器**（P18）—— L3 走的是"Key + curl"，**不要求装任何东西**
- ❌ **不接另两个同名"腾讯地图"口子** —— **指南制作 MCP**（改变不了本页面）与**官方地图 MCP**（要额外 Key、与 WebService 重叠）。判定表 → `mcp-integration.md` §1 与 §4
- ❌ **不猜测坐标**
- ❌ **不承诺"路线规划可用"**（内置 Key 无此权限）
- ⚠️ **不得让用户误以为"全功能免 Key"** —— 见 §2
- ❌ **不得用直线连点却写"路线图"** —— 只连直线的叫「**点位与顺序示意**」；即使喂了真实路径点，也必须注明**非导航级**
- ❌ **不把 Key 写进 skill 或产物** —— Key 只存工作区本地；**产物里只有图**
- ❌ **不靠加大 `weight` 让线更醒目**（无效动作）；❌ **不给 `markers` 传 `color`**（无效动作）
