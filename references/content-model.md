## 1. 四象限的真义

四象限**不是"评价表"，是"一个矛盾的两轴展开"**：

```
                吸引力高（大家都想去）
                       ▲
                       │
   偏僻、去一趟成本大    │   排队、人多、预约难
   但确实好东西          │   但确实是经典
   ──────────────────────────────────▶ 代价高
                       │
   又远又一般            │   顺路但没什么意思
   不值得专门去          │   时间充裕可以打发
                       │
                吸引力低
```

- **纵轴** = 吸引力（"大家都想去"）
- **横轴** = 代价（"人多了大家又不想去"）

**它描述的是一个矛盾，不是一个评分体系。**
任何把它拆成"清净度 / 独特性 / 时间友好 / 交通便利"等多维加权打分的做法，**都是误读**。

> 🔧 **修正留痕**：本条曾被执行成"六维评分表"，被用户判定为"过度思考"并整体废弃。
> 依据：**出游是一个混沌的、多方面同时影响的过程，不是逐步理性计算。**

### 四象限落到页面上：两个作用，不是一个评价表（Q31 定）

四象限是**思考的框架**，不是**排版的结构**。落到景点卡上，它只有两个作用：

| 作用 | 对应轴的哪一半 | 在卡上的位置与权重 |
|---|---|---|
| **主张标签** + **一句话总结**（`.why`） | **吸引力轴**（为什么值得去） | **卡的上半**：图上的主张标签 → 倾向徽标 → 一句话总结。**金色 + 大字号** |
| **小提示**（`tip`） | **代价轴**（去了会怎样失望） | **卡的最底部一行**。**浅赭金底 + 一句话**，权重明显低于主张 |

> ★ **优缺点的权重必须不对称。** 上一版把"值得的理由 / 付出的代价"做成两个**并列等权**的字段块——
> 优点是段落、缺点也是段落，一样大声。读者读一张卡**像在听一场辩论**，读完不知道到底该不该去。
> **现行**：**主张占整张卡的上半，避坑只占最后一行。**
> **🔧 Q39 再收紧**：「值得的理由」这个**字段块整体删除**（用户判定"景点卡没有卡的感觉、内容太多"）——
> 它的职能**并入 `.why` 一句话总结**（那句话本身就是「值得去的理由」）；原「妙计」的职能**并入 `.spot-tip`（小提示）**。
> **现行主张 = 图上一枚标签 + 一行结论句；避坑 = 卡底一行。**
> 缺点不是不说，是**降权说**——读者先被打动，再被告知风险。这才是"军师给锦囊"的口气。

> ✅ **契约层已同步（`攻略内容Schema-草案.md` v0.13）**：字段名统一为 **`why` / `tip`**，`appeal` 与 `tactics` 已从契约层删除。
> 改的是**权重与位置**：从"与优点并列的字段块" → "卡底一行"。**语义未变**（都指"代价轴"）。
> **两个文件口径一致，生成时不需要再判断以谁为准。**

## 2. 顶层目录：恰好 5 项

```
┌─ 封面 cover（页首，不是目录项）
│
① 行程总览 → ② 景点 ★ → ③ 每日行程 ★ → ④ 必读指南 → ⑤ 行程全貌
```

### ⚠️ 铁律：目录给人看，分类给机器用

内部资源分类（景点 / 美食 / 住宿 / 交通 / 打卡）**不等于**用户可见目录。

判断标准只有一条：

> **"一个普通游客打开页面，会不会去点它？"**

**不要为了整理方便的分类，端给用户当目录。** 十几个顶层模块，没人有耐心看。

### 各目录承载

| 序 | 目录 | 内容 |
|---|---|---|
| 1 | **行程总览** | **目的地 / 行程天数 / 同行人数 / 交通方式 / 预算**（行前须知并入这里） |
| 2 | **景点** ★ | **景点卡池**（核心，供横向比较、改倾向） |
| 3 | **每日行程** ★ | Day1…N 动线（**每天一块内嵌路线图**）+ 收拢美食 / 住宿 / 交通 / 打卡 |
| 4 | **必读指南** | 按**关键要素分组**的约束与提示条目（见 §3） |
| 5 | **行程全貌** | 一张 SVG 脑图 + 游玩要点口诀卡（**这里没有地图**） |

**为什么是「每日行程」在前、「必读指南」在后**（🔧 Q39 调序，重要级对调）：

- **跟着读者的使用顺序走**：先看"我每天怎么走"（这是攻略的主体，也是他照着执行的东西），
  再看"执行时要当心什么"。**把检查清单放在行程之前，读者会先读到一堆禁令，却还不知道禁令管的是哪一步。**
- **必读指南天然是"回查表"**：它每条都挂在某个景点或某一天上（`→ 影响：兴坪 / Day 2`），
  放在行程之后，读者遇到问题往回翻，路径更短。
- **每日行程因此升为核心项（★）** —— 它是这套攻略里唯一"照着做"的模块。

> 若需它更靠前（更"必读"）或更靠后（更像附录），调序即可，结构不变 ——
> 但**改序时必须全库同步"第 N 项"这类编号表述**（N12 令牌问题）。

### 不设"信息来源"目录

- **UGC 素材的出处不展示** —— 不写"这是从小红书某篇笔记看来的"。
- **公共资源信息必须带核实状态 + 一句权威依据**（见 §8）—— 标在条目上，不单列目录。
- 两者不冲突：**不展示的是 UGC 出处；必须展示的是公共资源信息及其依据。**

> **P8′ 口径**：公共资源信息必须标依据与核实状态；UGC 素材不出处。
> "有来源" ≠ "有效" —— 时效靠 `checked_at` 兜底。

## 3. 必读指南：按关键要素分组（每组一张分类图）

**内部标识 `pitfalls`，显示名"必读指南"。**

### 分组维度 = 关键要素（复用资源五类，不另造分类轴）

| 组 | 语义色 | 这个组收什么 |
|---|---|---|
| **🏛 景点** | `#2F5D7E` 石青 | 实名预约 / 预约渠道 / 闭馆日 / 亮灯时间变更 / 停止入场 / 最佳时段 / 单向通行 |
| **🍜 美食** | `#B5502A` 朱磦 | 排队长短 / 营业时段（只做早市）/ 网红店 vs 本地店 / 计价方式 / 景区内物价 |
| **🏨 住宿** | `#6B4A73` 紫檀 | 位置陷阱（看着近实则绕）/ 押金退改 / 老楼无电梯 / 隔音 |
| **🚇 交通** | `#3A6E78` 沧浪 | 导航定位陷阱（同名不同点）/ 该时段打不到车 / 交通管制 / 换乘要点 / 末班时间 |
| **📸 打卡** | `#A83A5C` 胭脂 | 机位要抢 / 光线时段 / 收费合影 / 禁飞区 |

- **分组顺序固定**：景点 → 美食 → 住宿 → 交通 → 打卡。
- **空组不渲染** —— 某地没有住宿坑就不出现紫块，**不为凑齐五色而编内容**。
- **每组顶部一张分类实景图**（拍什么见 `spot-images.md` §9）。语义色**只出现在组名前的 9px 色块里**。

### 渲染规则

- **组容器**：**白底卡 + 顶部一张分类实景图**（图向下渐淡融入卡面）；★ **两栏瀑布流**排布（`columns:2` + `break-inside:avoid`），`≤1000px` 转单栏 → 两组**各自顶到上方**，不等高。
  ~~浅底（组色 10%）+ 左侧 3px 组色竖条~~ —— Q31 废止：五块不同色的底叠在一页就是"花"。
  **一套颜色只背一个语义，但不铺面积**：分组色只剩组名前的 9px 色块。版式细节见 `design-system.md` §4「分类块版式」。
- **标题在前，徽标在后** —— 先读到"是什么"，再读到"什么级别"。
  **不要把徽标顶在句子前面**：视线先撞上分级、后看到内容，反而读不进去。
- ★ **每条只在标题前放一个 8px 点**（**不用文字徽标**）：`hard`「必读」**暗红** / `soft`「提示」**暗黄**。
  🔧 **Q42 定稿**：文字徽标（药丸）整体废弃 —— 用户判定 *"观感不好，直接不要这个标签"*。
  **点放在信息前**（读作「·必须提前实名预约」），不占标题的注意力。
  🔧 **Q39 留痕**：再之前是「🚨 会毁行程」「💡 体验提示」（字长、带 emoji、实心红）。
- **核验行只有一种形态**：`✅ 已核验（基于{来源大类}）`（大类限 **腾讯地图 / 官方渠道 / 公开信息**）。
  **"未核实"不上页面**（不写来源、不写未核实、不写日期）—— 由页脚一句兜底说明。
- **每条可挂钩**：显示"→ 影响：洪崖洞 / Day 2"。
- **折叠（按条，不按组）**：`hard` 直接列出；`soft` 收进该组的 `details`，摘要写「提示 N 条 · 点击展开」。
  ★ **`details` 一律默认收起 —— 摘要文案必须与初始状态一致**（写"点击展开"就不能是展开态）。
- 🔧 **Q42 废止本条"例外"**：曾写"某组一条 `hard` 都没有时默认展开"。实测（川西 · 打卡组）变成
  **摘要写着"点击展开"、实际已经展开** —— 自相矛盾，结构约束当场失效。**现一律收起**；
  整组全是软信息时，收起态本身就传达"这一组都是建议，不是硬约束"。

### 每条避坑的字段

| 字段 | 说明 |
|---|---|
| `title` | 一句话（≤ 20 字），如"必须提前 3 天实名预约" |
| `detail` | 补充说明 / 具体怎么做 |
| `verify` | 数据层字段：已核验 / 未核验 —— **页面呈现只有"已核验"一种标记，"未核实"不上页面**（不写来源、不写未核实） |
| `source` | 公共资源信息的一句权威依据（如"景区官方小程序"） |
| `severity` | `hard` → 标题前**暗红点** / `soft` → 标题前**暗黄点** —— **只做点，不做分组**。判据：**会影响成行（预约 / 限流 / 闭园 / 管制 / 抢房）→ `hard`；怎么做更好（机位 / 光线 / 口味）→ `soft`** |
| `affected` | 挂钩：这条坑影响哪个景点 / 哪一天 |

> **色块只背一个语义**：颜色 = 分组标识；严重度 = 徽标。**不能让一套颜色同时表达两件事。**
>
> 🔧 **修正留痕**：本 skill 上一版按"严重度分两区 + 性质分组（预约与票务 / 开放与时间 / 交通与抵达）"设计，
> 用户指出**应按关键要素分组**。要素维度更优：① 和用户翻攻略的**检索心智一致**（想的是"我在看景点这块"）；
> ② **复用已有的资源五类**，不多造分类轴；③ 原"性质分组"粒度太细且互相重叠（"导航定位陷阱"算交通还是景点？）。
> **"显著风险"没丢** —— 它从"分区"降为"每条上的**暗红点** + 组内排序优先"。

## 4. 中枢对象：景点卡

### 4.1 景点是主轴，其余是卫星

- **景点走完整编排**（聚类 / 时间 / 动线）
- **附加品（`addon`）不独立编排**，只带 `anchor` 锚点挂载

理由：**"美食值不值得"高度依赖"你那天在哪"。**

### 4.2 景点卡 = 倾向 + 主张 + 避坑（+ 事实芯片）

```yaml
spot:
  name: 洪崖洞
  stance: 值得          # 必去 / 值得 / 可选 / 可跳（定性，禁止数字）
  tagline: 免费 · 城市名片   # ① 主张标签：固定两段「费用」「定性」，合计 ≤16 字；无图标
  why: 全国少见的立体夜景，临江吊脚楼层层叠叠   # ★ 卡上那句话（≤26 字）—— 它就是「值得去的理由」，卡的结论行，必填；**卡面不出现字段名**（Q40）
  tip: 旺季排电梯要 40 分钟，且是改造过的商业街，别期待"古镇感"   # ④ 小提示（必去 ≤40 字 / 值得·可选 ≤20 字）
  facts:               # ③ 事实芯片：必去 ≤4 条 / 值得 ≤3 条 / 可选 ≤2 条；字段名限字典
    - [门票, 免费]
    - [时长, 1.5–2 小时]
    - [开放, 全天]
  verify: 已核验        # ✅ 已核验 / 未核验（**页面只呈现"已核验"这一种标记**）
  source: 洪崖洞景区官方公告（2026-08-01）
  checked_at: 2026-09-21
xhs:                    # 卡**外**、卡下方，两个标签并排（Q42：**按钮文案固定，不含景点名**）
  - [小红书·游玩攻略, "{景点名} 游玩攻略"]   # 前段 = 按钮文案；后段 = 搜索词
  - [小红书·拍照参考, "{景点名} 拍照参考"]
```

> ★ **卡面上不出现字段名（Q40 用户判定）**：`why` 在卡上**就是那不带头尾的一句话**；
> `spot-tip` 前有一个固化的 `<b>小提示</b>` 前缀，仅此一个。
> **`一句话总结` / `值得的理由` 这类词一个都不上卡面** —— 用户原话：
> *"如果这个是完整 title 是不对的，排版就是一句话，也就是倾向徽标。"*
> 即：**它和倾向徽标同属「一眼判断区」** —— 读者一眼看到的判断，不是**要先读标题才知道是什么的表单字段**。

**① `tagline`（主张标签）怎么写** —— 它是全卡**唯一压在实景图上**的一枚标签，也是读者决定"要不要往下读"的第一眼信息。**固定两段，不得改结构**：

| 段 | 内容 | 上限 |
|---|---|---|
| 第 1 段 | **费用**（票价或人均；免费就写"免费"） | 8 字 |
| 中间 | ` · `（中间点） | — |
| 第 2 段 | **定性**（一句话说清它的定位） | 8 字 |

- ✅ `免费 · 城市名片` ／ `约 255 元/人 · 山水精华` ／ `5 元 · 20 元背景`
- ❌ `这个景点要收 255 块钱一个人，是整条漓江最精华的一段` —— **这是句子，不是标签**
- **定性必须携带信息**：`山水精华` ✅ ／ `必打卡` ✅（说明它是最常见的打卡点）／ `此生必去` ❌（口号，删掉不损失信息）

**③ `facts`（事实芯片）** —— 字段名只能用字典：`门票` / `时长` / `开放` / `预约` / `交通` / `位置` / `人数限制` / `排队`。
**一条 ≤14 字、一张卡 ≤4 条；字典外的事实归入正文**（不要硬塞，塞不进说明它该是一句话）。
**芯片不是"参数堆"**：只放**会影响决策**的那几条；查得到的琐碎参数不必上卡。

> **主张与避坑的完备度不是一刀切**：
> - `必去` / `值得` —— **主张与避坑都要写**（用户要靠"小提示"决定到底去不去、怎么去）；
> - `可选` / `可跳` —— **可只留「小提示」一条**。这类项的决策重点就是"值不值得为它花时间"，
>   本来就不缺吸引力，缺的是风险说明。**这不是偷工，是把笔墨用在刀刃上。**

### 4.3 ★★ 卡片体量上限（Q39 立）

**三组景点卡都进两列网格**（`.grid.g2.spotgrid`），所以**同排两张卡的高度不能差太多**，否则页面出现"一长一短"的参差。

| 倾向 | `why` 一句话总结 | `tip` 小提示 | 事实芯片 |
|---|---|---|---|
| **必去** | ≤26 字（1 行） | **≤40 字（≈2 行）** | ≤4 条 |
| **值得** | ≤26 字（1 行） | **≤20 字（≈1 行）** | ≤3 条 |
| **可选** | ≤26 字（1 行） | ≤20 字（≈1 行） | ≤2 条 |
| **可跳** | ≤26 字（1 行） | ≤20 字 | 无（折叠区，不带图、不带小红书标签） |

> **判据**：**必去卡最多比值得卡多 3 行内容**（算上空行约 6–8 行的视觉增量），不能再多。
> **写超了怎么办：把超出的部分移进「必读指南」** —— 那里本来就按要素分组、还能展开。
> **卡片负责"一眼看懂"，必读指南负责"逐条细看"，两个模块各司其职**，不要互相挤压。

### 4.4 ★★ 数量上限：推荐几个景点 = 生成几张图（D22）

**用户裁定**：*"约束推荐景点数量，也就是 AI 生图上限。"* —— **选几个景点，就是把生图预算定几。**

| 项 | 上限 | 理由 |
|---|---|---|
| **景点卡总数** | **≤ min(天数 × 3, 12)** | 3 天 → ≤9；5 天 → ≤12；7 天 → ≤12（**硬顶**） |
| **其中「必去 + 值得」** | **≤ min(天数 × 2, 12)** | 每天最多 2 个核心点 —— 这是**行程可行性**的上限，不是图片预算 |
| **封面** | **1 张** | 最多出现 1–2 个地标，不随景点数扩张 |
| **必读指南分类图** | **≤5 张**，**只为有内容的组生成** | 空组不渲染、不生成 |
| **每日路线图** | **≤天数**张，**不算 AI 生图** | 走地图 API，配额按接口分项另算 |

**AI 生图总账：≤ 1 + 12 + 5 = 18 张**（单张 5–10 credits → **约 90–180 credits**）。

**四条纪律**：

1. **生成前先报账** —— 报**总张数 + 预估 credits**，**不默默开跑**。
2. **失败即降级、不重试。**
3. **降级顺序：分类图先降**（它本来就可以不存在）**，景点图最后降**（决策核心）。
4. **不为凑数加景点** —— 上限由**行程可行性**决定，不是由"图能画几张"决定。

## 5. 附加品：挂在景点上

```yaml
addon:
  type: food            # food / hotel / transport / photo
  name: 花市豌杂面        # ★ 餐饮类**必须写真实店名**，禁止"附近找家面馆"
  anchor: spot:洪崖洞    # 锚点：玩这个景点时顺路
  why: 本地人早餐，10 块钱一碗          # 一句话总结（≤26 字）—— 这一句就是"值不值得"的答案
  tip: 环境很一般，排队可能要 20 分钟    # 小提示（卡底一行，权重低于 why）
  verify: 已核验          # ✅ 已核验 / 未核验（**页面只呈现"已核验"这一种标记**）
  source: 腾讯地图 POI 检索（2026-09-22）
  checked_at: 2026-09-22
```

### ★★ 「吃什么」是刚需，必须写店名（Q39 立）

**用户判定**：*"吃什么必须写店名，它的作用和景点一样重要 —— 对齐小红书攻略，说明是刚需。"*

| 要求 | 说明 |
|---|---|
| **每个用餐节点都写店名** | 时间线里 `li.food` 的 `{餐次 · 店名}` 不得留空、不得写"附近找家 XX 店"。5 天行程约 10–15 个餐点，逐个落实 |
| **店名从哪来** | 有腾讯地图 Key → `place/v1/search`，用 `boundary=nearby(景点坐标,半径)` 找"**这一带吃什么**"，拿**真实店名 + 地址 + 坐标**；没 Key → 用可靠公开资料 —— 页面**照常写店名，但不加核验行**（"未核实"不上页面） |
| **每条给三样** | **推荐菜**（点哪几道）· **一句理由**（为什么选它）· **与上一站的距离 / 关系**（顺不顺路） |
| ★ **不给门牌地址** | ❌ **不写 `XX区XX路X号X楼` 或「XX酒店旁」这类门牌** —— Q40 用户判定 *"这种地址不应该给，而是给关键信息，推荐哪些菜"*。读者要的是"点哪几道菜"，不是门牌号；**定位只到「与上一站的距离 / 关系」为止** |
| **推荐菜写在哪** | 写进**餐饮节点的说明**（`li.food` 的 `.d`）或 `addon.why` —— **不新造字段**（契约层 v0.13 已定稿） |
| **核实与依据** | 店名与位置属**公共资源信息**。数据层带 `verify` + `source` + `checked_at`；**页面上只呈现一行** `✅ 已核验（基于腾讯地图）` —— **不写具体接口名、不写日期**（日期由页脚统一交代） |
| **推荐菜与人均** | 地图接口**不返回**这些 → 来自公开资料或模型判断时，**语气上要区分开**（写"以啤酒鱼出名"，不要写成像核实过的参数） |
| **进不进内嵌地图** | ❌ **不进** —— `markers` 的颜色参数实测无效（N26），餐厅图钉和景点图钉**在图上长得一模一样**，加上去只让读者混淆。要表达"顺不顺路"，用**文字里的距离**（"离象鼻山 1.2 km"） |

> ★★ **店名是"事实"，不是"建议"** —— 它和票价一样要能溯源。
> 找不到可靠店名时，**宁可如实说明（不加核验行），也不要编一个听起来很像的店名**。

**锚点三种**：

- `spot:xxx` —— 玩某景点时顺路
- `day:N` —— 这天住哪
- `leg:N-M` —— 第 N 到 M 天之间（交通）

> **景点卡与附加品思路完全同源**（都是"主张 + 避坑"两层），**但编排不同源**（景点独立编排，附加品挂载）。

## 6. 倾向与理由

**倾向徽标上只写一个词**（`必去 / 值得 / 可选 / 可跳`）；**注解归分组标题**，不要贴在徽标上（徽标塞注解 = 标签超载，见 `design-system.md` §6）。

| 倾向 | 含义 | 分组标题写法 |
|---|---|---|
| **必去** | 不可替代 —— 缺了它这趟不成立 | `必去 · 不可替代` |
| **值得** | 有明确收获，推荐安排 | `值得 · 有明确收获` |
| **可选** | 非必需 —— 顺路就去 | `可选 · 非必需` |
| **可跳** | 性价比低，不推荐 | `已排除的选项 · 不去的理由` |

- **每条必须附一句话理由。** 不允许只给倾向不给理由。
- **禁止任何数字评分 / 百分比 / 推荐指数。**
- **用户决策方式** = 改倾向，或改理由那句话。
- **`可跳` 的项要展示** —— **列出但默认折叠**。"什么被排除了、为什么"本身就是重要的决策信息。

## 7. 信息深浅：分层折叠

| 层 | 内容 | 默认 |
|---|---|---|
| **封面层** | 城市名 / 日期人数 / 封面图 | ✅ 展开（页首） |
| **决策层** | 去哪、几点、为什么、要注意什么、倾向；必读指南「必读」条目 | ✅ 展开 |
| **细节层** | 历史背景、门票细则、交通细则、备选方案、拍照机位、`可跳` 项；必读指南「提示」条目 | 🔒 折叠 |

**不设"档位"开关**（如"简版 / 标准版 / 详细版"）——那是在让用户做无谓的选择。

## 8. 事实与推理必须分离

| 类型 | 来源 | 要求 |
|---|---|---|
| **事实**（坐标 / 距离 / 时长 / 票价 / 营业时间 / 预约规则 / **店名与位置**） | 外部能力或联网检索 | **必须带核实状态**（见下） |
| **推理**（值不值得 / 怎么排 / 提醒） | 模型判断 | 是判断不是事实，语气上区分开 |

### 8.1 每条事实必须带三样东西

```yaml
facts:
  - label: 开放
    value: 全天；灯饰 19:30 开、23:00 熄
    verify: verified          # verified / unverified
    source: 景区官方公告        # 一句简单文字的权威依据
    checked_at: 2026-09-21    # 什么时候核实的
```

**硬规则**：

1. **未核验不影响列出** —— 照样列，**但不加任何标记**（"未核实"不上页面）。这是**风险管控的显性呈现**，不是删掉不给人看。
2. **`source` 是一句简单文字，不是链接堆** —— 不展示"参考了哪几篇文章"。
3. **绝不以确定语气输出无来源的事实。**
4. ★ **"有来源"不等于"有效"** —— 票价 / 开放时间 / 亮灯时间 / 预约规则**都会变**。
   此类事实**必须做时效性核验**：**优先取最近的通知 / 官方公告**。

> **完整可信度 = `verify`（有没有核实）× `checked_at`（什么时候核实的）。**
> 二者缺一，这条事实就不可用于决策。

### 8.2 时效性为什么是硬规则

同一景点，网上常同时存在**前后两版**开放/亮灯时间，攻略站还常引用已过时的那一版。
因此：**检索到多个说法时，取时间最近的那一份**，并把 `checked_at` 记为核实当天。

> 反向信号：若某攻略说"网上很多攻略写的时间已经过时了"，**这本身就是时效性问题的证据**，
> 说明该字段必须重新核验，不能沿用。
