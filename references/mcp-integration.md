## 1. 先分清三个"腾讯地图"

同一个名字底下是**三个互不相干的口子**。混在一起会得出错误结论 ——
**典型误判："我配了腾讯地图 MCP，应该就能出路线图了吧？"（配了也不行）。**

| # | 口子 | 形态 | 门槛 | 影响产出？ | 能干什么 |
|---|---|---|---|---|---|
| **③** | **WebService API** | **裸 HTTP 请求**（**不是连接器**） | **自备 Key** | ✅ **唯一影响产出** | 算路况 / ETA / N×N 耗时 / 静态图 → **L3 内嵌路线图** |
| ① | 腾讯地图·指南制作 MCP | WorkBuddy 连接器 | 微信扫码（免 Key） | ❌ **不影响网页** | 把行程**落进腾讯地图 App**（交付之后的第二个出口） |
| ② | 腾讯地图 官方地图 MCP | 独立连接器 | **需自备 Key** | ❌ **不接** | 地图类工具；与 ③ 能力重叠、还要多一把 Key |

**判据只有一条：它能不能改变交付的那个 HTML？**
① 和 ② 都不能。**"要不要配连接器"与"页面里能不能长出地图"，是两件事。**

> **顺带纠一个常见误判**：**③ 根本不是连接器，是 HTTP。**
> 所以"连接器面板里显示已连接"这件事，对路线图**一点帮助都没有** ——
> 它只差一把你自己申请的 Key（申请 4 步见 `map-capability.md` §2）。

### 1.1 最容易混的一对：「地图嵌进 HTML」≠「攻略存进地图 App」

两个都叫"腾讯地图"，**产物却落在完全不同的地方**。这一条是 **Q34 用户亲自澄清**的误读，
写在这里，防止下一个人再绕一圈：

| 你真正想要的 | 用哪个 | 产物落在哪 | 交付的那个 HTML 会变吗 |
|---|---|---|---|
| **把地图画进页面**（不跳转、离线也能看） | **③ WebService `staticmap/v2`** | **HTML 里多一张 base64 内联图**（`.routewrap` 块） | ✅ **会** |
| **把攻略存进腾讯地图 App**（"我的行程"里能看到、能导航） | **① 指南制作 MCP** | **你腾讯地图账号里的一条指南** | ❌ **不会 —— 页面里一点都看不见** |

> **一句话记住**：**"页面里有地图"走 ③；"手机地图 App 里有行程"走 ①。** 两者**互不替代、互不蕴含**。
>
> ★ **③ 不需要在连接器面板里配置任何东西** —— 它不是连接器，只要一把你自己申请的 Key
> （粘贴给 agent，或设环境变量 `TMAP_WEBSERVICE_KEY`）。
> 所以「我把指南制作 MCP 连上了」**不会**让页面里长出地图；反过来配了 ③，
> **手机地图 App 里也不会多出一条行程**。

## 2. WebService API（**唯一影响产出的外部能力**）

> **这是唯一一条能让"地图长在页面里"、能算"这段路几点最堵"的路。** 腾讯地图的能力分成三条路，只有这条能算路况：

| 路径 | 是什么 | 能算路况 / 时间吗 | 说明 |
|---|---|---|---|
| ① 免 Key Claw 页面 | `nearby-search` / `travel` / `trail-map` | ❌ **不能** | 内置 Key **只有「地图展示」权限**，路线规划直接报「路线规划失败」 |
| ② 腾讯地图·指南制作 MCP | 攻略 → 地图指南 | ❌ **不能** | 它是**交付出口**；2.0 契约明文规定「**服务端不计算路线**」，`polyline` / `route_ext` 须由调用方提供真实算路结果 |
| ③ **WebService API** | `direction/v1/*`、`traffic_status`、`distance/v1/matrix`、`staticmap/v2` | ✅ **能** | **必须自备 Key**（**Q35 已实测跑通**：静态图 / 路线规划 / 批量算路 / 地点搜索） |

### 能拿到的四样东西

| 接口 | 能力 | 解决什么 | Q35 实测 |
|---|---|---|---|
| `direction/v1/driving` | policy 支持**实时路况 / 躲避拥堵**，返回**结合路况的 ETA** | 去程 / 返程耗时预估 | ✅ 通 —— 返回**真实道路路径**（polyline）+ ETA + 红绿灯数 + 打车估价 |
| `traffic_status` | **分钟级更新 + 可查过去 3 个月历史路况** | **事前知道"这段路常态就是堵"** | ❌ **路径未测通**（`traffic/v1/*` 报 `status:404 错误的请求路径`）→ **暂不接入，也别写进交付承诺** |
| `distance/v1/matrix` | 一次算 **N×N** 两两耗时 | 景点间动线的**批量**时间预算校验 | ✅ 通 |
| **`staticmap/v2`** | **一张画好点位与连线的静态图** | **L3 内嵌路线图**（图长在页面里，不跳转） | ✅ 通 —— 出真图（600×400 PNG **420 KB**），需本地转 JPEG 压体积 |

> 另有 `place/v1/search`（地点搜索）· `place/v1/suggestion`（联想）· `geocoder/v1`（逆地址解析）**均实测可用**，
> 用于**补坐标**。完整接口清单与 status 码表 → **`map-capability.md` §2**。

**获取 Key**：访问 `https://lbs.qq.com/dev/console/application/mine`，创建 **WebServiceAPI** 类型的 Key
→ ★ 然后去[**配额页**](https://lbs.qq.com/dev/console/quota/account)看「已分配/总额度」并点「**一键分配**」，把额度分给要用的接口。
**这是最容易漏的一步** —— 漏了就是"Key 明明申请了却一调就报错"。

**⚠️ 配额现实（Q35 实测）**：配额**按接口分项**计，且新建应用额度可能极低 ——
一把刚申请的 Key，`staticmap` **第 1 次成功、第 2 次起就报
`{"status":121,"message":"此key每日调用量已达到上限"}`**；其余接口各成功一两次后同样 121。
**这不是 Key 有问题，是额度没分配**。排查：`python scripts/make_route_map.py --probe`。

**Key 存放**：`.workbuddy/tmap_key.txt` 或环境变量 `TMAP_WEBSERVICE_KEY`。
⚠️ **绝不写进 skill 文件、不提交仓库、不贴公开对话** —— **产物里只有图，没有 Key**，转发是安全的。

**实测结论**：无 Key 调用返回 `{"status":311,"message":"key格式错误"}` —— 没有 Key 时这些接口完全不可用。

### 为什么它从"可选"升级为"**建议配置**"

因为**"拥堵"是行程规划的第一风险，而它只能靠这条解**。

> **杭州实例**：下午 5:10 从西湖到萧山机场，地图上"很近"，出租实际开了 **2.5 小时**。
> **看起来近 ≠ 实际快。行程规划的第一风险不是距离，是时间的不可预测性。**

`traffic_status` 的**历史路况**，让"看起来近、实际很慢"这件事**在出发前就能被看见**。

### ⚠️ 但边界要说清（不要过度承诺）

| 难题 | 能不能靠工具解 |
|---|---|
| **拥堵** | ✅ **能**（有接口） |
| **排队** | ❌ **不能** —— **没有这个接口**。只能靠景点卡 `tip` 的经验描述 + 时段策略（早上去） |

> **别把"排队"也承诺成能算。拥堵可解，排队无解** —— 这个诚实的边界比虚假的全面更有价值。

## 3. 三级事实供给链（**每条都要带核实状态**）

本 skill 处理"事实类信息"（坐标 / 距离 / 时长 / 票价 / 营业时间 / 预约规则）的顺序：

| 级 | 来源 | 标注要求 |
|---|---|---|
| **A** | **宿主已有能力**（用户已连的地图 / 旅行类连接器） | 正常呈现 |
| **B** | **联网检索** | 页面**不加核验行**（"未核实"不上页面） |
| **C** | 都没有 | **标注缺失，或不输出这一条** |

**每条事实在数据层带** `verify` / `source` / `checked_at`；**页面上只呈现一行** `✅ 已核验（基于{来源大类}）`（大类限 **腾讯地图 / 官方渠道 / 公开信息**）—— **不写具体接口名、不写日期**。

> **铁律 ①：绝不以确定语气输出无来源的事实。**
>
> **铁律 ②：「有来源」不等于「有效」。**
> 票价 / 开放时间 / 亮灯时间 / 预约规则 / 交通管制**都会变** —— 此类事实**必须做时效性核验**：
> **优先取最近的通知 / 官方公告**，并记录 `checked_at`。
>
> **实测案例**：重庆洪崖洞的亮灯时间，检索同时命中"夏季 19:00"与"2026-09-03 起改 19:30"两个说法 ——
> **后者才是当前有效值**。攻略站里那句"网上很多攻略写的 19:00 已经过时"，就是时效性问题的铁证。
>
> **⚠️ 未核验的条目照样列出来**，但**不加任何标记**（"未核实"不上页面）—— 这是**风险管控的显性呈现**，不是删掉不给看。

## 4. 明确不接的能力（黑箱禁区）

| 能力 | 为什么不接 |
|---|---|
| 任何 MCP 的「AI 一键生成行程」功能（如飞猪 `travel_plan`） | **黑箱行程生成器**：它会代排行程，架空本 skill 的核心编排逻辑与"理由优于解释"原则 |
| 任何"输入目的地、输出完整攻略"的能力 | 同上——那就不是在用本 skill 了 |
| **腾讯地图 官方地图 MCP**（`tencent-map`，需 Key） | **能力与 §2 重叠，却要多一把 Key**；本 skill 只用得上"算路况 / 出静态图"，裸 HTTP 已覆盖，**不值得引入连接器依赖**（P18） |
| **腾讯地图·指南制作 MCP**（`tencent-map-guide`） | ⚠️ **不是"不能用"，而是"改不了产出物"** —— 它改变不了那个 HTML，只做**交付之后的第二次投递**（见 §5）。**主流程不依赖它，也就不把它写进流程** |
| **小红书 MCP**（扫码登录个人号自动读笔记） | 见下方专述 |

### 小红书 MCP：为什么不做（判断依据，值得记住）

小红书 MCP 技术上**真实可行**（有活跃的开源实现，能搜笔记、读正文与评论）。
**但本 skill 明确不做**，理由是用户 Q23 的判断：

> **"小红书的经验主要就是有真实用户的踩坑经验受到大家追捧……实际上高赞的小红书内容也不是基于真实用户生成的。"**

**L3′ 的全部价值，建立在"内容是真实用户经验"这个假设上。**
而**这个前提本身就不成立**（高赞内容大量是机构 / 团队运营产出）。既然收益不存在，就不值得付：

- **账号风险** —— 要用个人号跑自动化
- **分发代价** —— 别人装了还得自己 Docker 部署 + 扫码，破坏"即装即用"
- **维护成本** —— 依赖前端结构，改版即失效

**替代方案（已采纳）**：**跳转按钮** —— 规划完成后，在页面里放一个按钮跳到**小红书已搜好的结果页**，
浏览发生在用户自己的 App 里。**零门槛、零风险。**

| 位置 | 按钮文案（展示文案 = 搜索词） |
|---|---|
| 景点卡**外**、下方并排（左） | **`小红书·游玩攻略`**（搜索词 `{景点名} 游玩攻略`） |
| 景点卡**外**、下方并排（右） | **`小红书·拍照参考`**（搜索词 `{景点名} 拍照参考`） |

> 🔧 **Q40 同步**：本表原为「景点卡片内 / 打卡 `photo` 项内」，且第二个词写着「小白出片」——
> 那是**我们起搜索词时的站内黑话**，用户判定不上页面（详见 `writing-style.md` §7-7）。
> **这处漏改是自检器 `check_consistency.py` 抓出来的**（N12：改了体系必全库扫过时令牌）。
>
> 🔧 **Q42 再收紧**：**按钮上不再写景点名** —— 长名字会撑成两行（实测「四姑娘山双桥沟 游玩攻略」）。
> 按钮文案固定为 `小红书·游玩攻略` / `小红书·拍照参考`，**单行不换行**；**搜索词不变**。

> **方法论**：判断要不要接一个能力，看的是**收益是否真实存在**，
> 而不是"多一个选项总没坏处"。**"留口"本身不等于"该留"。**

## 5. 留档：指南制作 MCP 实测记录

> **本节是留档，不是流程步骤。** 若有人问"能不能把攻略导进腾讯地图 App"，答案在这里；
> **产出页面不需要读本节。**

**它是什么**：把一份**已经排好**的行程转成腾讯地图里的一条结构化指南，存进用户自己的地图账号，App 内可直接导航。
**门槛**：微信扫码（OAuth），**免开发者 Key**，一次授权长期有效。
**它的位置**：**交付之后的第二个出口** —— 与"单个可分享 HTML"**并列**，不是它的前置。

**为什么不算进流程**（三条，任一条已足够）：

1. **改变不了 HTML** —— 判据见 §1；
2. **替代不了算路** —— 2.0 契约**明文规定"服务端不计算路线"**，`polyline` / `route_ext` 必须由调用方给真实算路结果 → **换算路仍只有 §2**；
3. 它是**第二个投递通道**，不是本 skill 的产品形态（本 skill 的交付物是**单个 HTML**）。

**若确认要接**（2026-09-22 实测，本机 `connector:tencent-map-guide` 已连通）：

| # | 工具（**在线实名 = 唯一权威**） | 用途 |
|---|---|---|
| 0 | `travel_guide_getspec_doc` | **取当前规格文档（调用前必做）** |
| 1 | `travelguide_v2_create` / `_update` / `_getinfo` / `_delete` | 增 / 改 / 查 / 删 |
| 2 | `wb_guide_convert_v2` | 已有现成文本时的转换口 |

**6 条会真踩的坑**（**照抄官方附带文档必失败**）：

- ⚠️ **连接器自带的说明文档停留在 1.0**（教的是 `create_guide` / `save_guide_ai` 传 Markdown）——
  **这些工具在在线工具面上已不存在**。
- `spec_version` **必须** `"2.0.0"`，**不静默降级**（否则 `12003`）。
- `item_order[]` 是组内顺序**唯一权威**：一旦非空，**必须列全**该组全部元素与直接子组，
  缺项 / 悬空 / 重复直接 `21002` —— **服务端不猜意图**。
- `polyline` 轴序是 `Δlng,Δlat`（**经度差在前**），而只读回填的 `route_info` **轴序相反** —— **写反就是画错线**。
- `guide_slug` **留空会产生重复指南**（命中才返回 `21007` 幂等成功，**仍返回原指南 ID，可直接用**）。
- 日期写在 `group_ext.ext.related_date` 里（**不是分组的一级字段**）；`group_id` 与 `element_id` **共用同一 ID 空间**。

**两个顺手收益**：`share_req.need_url=true` → 返回 **H5 分享链接**；`need_miniprogram_qrcode=true` → 小程序码。

> **这条实测最大的价值不是"能接"，而是它给出的通用教训** —— 已提炼为 SKILL.md 铁律：
> **工具名以运行时 schema 为准，永不照抄官方附带文档。**
> （同类坑的历史：`tmap-lbs-plugin` 官方文档把 `recommend` 写成多值，**实际只认单值**。）

## 6. 一句话总览

| 能力 | 门槛 | 是否必须 | 在本 skill 中的位置 |
|---|---|---|---|
| **地图链接**（`map-capability.md`） | **零**（可看不可交互） | **自带** | 位置可视化（**每日行程内嵌路线图**） |
| **封面图源**（`cover-image.md`） | **零** | **自带** | 封面 |
| **腾讯地图 WebService API** | **自备 Key + 配额分配** | **建议配置** | ★ **唯一加档项** —— L3 内嵌路线图 + 时间计算。**Q35 实测**：静态图 / 路线规划 / 批量算路 / 地点搜索**均跑通**；**路况端点路径未测通**（暂不算数） |

> **本 skill 的底线：没有任何外部能力，也能产出完整可用的攻略网页。**
> 但如果你在意"时间算得准不准"，那把 Key 配上是值得的 —— **因为拥堵只能靠它解。**
>
> 另有两个同名"腾讯地图"口子（指南制作 MCP / 官方地图 MCP）**已被排除**，判定与理由见 §1、§4。
> **「地图嵌进 HTML」与「攻略存进地图 App」的对照表** → §1.1。
